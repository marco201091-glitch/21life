# Audit miglioramenti 21Life — 1 ottobre 2026

Il progetto supera i controlli di qualità, ma presenta problemi concreti di affidabilità operativa, completezza dei dati e distribuzione. Prima di ampliare le funzionalità, conviene chiudere i punti 1–5. Non sono state applicate correzioni, migrazioni o modifiche remote.

## Perimetro ed evidenze

- Repository aggiornato con `git fetch origin --prune`. Checkout esaminato: `f6f1670`; `origin/Dev`: `29316af`; `origin/main`: `b11b203`. Differiscono soltanto nella checklist, quindi codice e lockfile verificati corrispondono a entrambi i rami remoti.
- `npm run quality` e `npm --prefix expo run quality`: superati, inclusi lint, typecheck, coverage e dipendenze inutilizzate. **258 test web + 249 Expo = 507 test**, 150 file. Coverage statement: web 57,57%, Expo 70,76%, limitata ai moduli inclusi dalle configurazioni.
- `npm audit --omit=dev --json`: web **1 segnalazione critica Next.js**; Expo **0**. Gli audit sono separati dal comando locale `quality`.
- CI sugli SHA remoti attuali: [Dev](https://github.com/marco201091-glitch/21life/actions/runs/36708327345), [main](https://github.com/marco201091-glitch/21life/actions/runs/36703556440), entrambe verdi il 30 settembre. Verificati gli step: migrazioni e lint SQL, build web, budget, E2E browser e live, qualità/export Android. Sono esecuzioni precedenti, non nuove build locali: il nuovo risultato npm dimostra che una CI verde non certifica l'assenza futura di advisory.
- Produzione `/api/ready`: HTTP 200, versione 9.0.4, commit `b11b203`, database ready, 57 ms nella singola lettura. Questo non misura disponibilità storica o prestazioni sotto carico.
- Protezioni Dev/main: richiesti `web` e `expo`, amministratori inclusi, force push disabilitato. Readiness Obtainium `--release` superata.
- Nessun file reale `.env`, chiave privata o keystore trovato nei nomi tracciati controllati; ricerca mirata dei pattern GitHub/AWS/private key sui due rami senza match. Non è una scansione completa di tutti i segreti nella storia.

## Interventi prioritari

### 1. Alta — aggiornare Next.js e rieseguire il gate di sicurezza

`package.json:89` e lockfile fissano Next.js **16.3.5**. L'audit rileva [GHSA-vcvr-r3jv-pc5j](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j), relativo a esecuzione di codice in `next/og ImageResponse`; la correzione parte dalla 16.3.6. npm propone 16.3.8, senza salto major.

**Distinzione:** gravità critica della dipendenza; sfruttabilità nell'app non dimostrata. La ricerca in `app`, `components` e `lib` non trova `next/og` o `ImageResponse`. L'advisory richiede valori controllati dall'attaccante inseriti in SVG nel renderer Node.js.

Intervento: aggiornamento patch compatibile, quality/build/E2E e nuovo audit. La PR Dependabot #128 è già verde, ma va controllato il suo contenuto prima di usarla come correzione. Accettazione: versione fuori dal range vulnerabile e audit produzione senza questa segnalazione. Aggiungere un audit programmato indipendente dai push.

### 2. Alta — rendere atomici migrazione e registro

`scripts/selfhosted-db.mjs:92` esegue `runPsql(sql)`; la successiva chiamata registra checksum e versione. Ogni chiamata apre una **transazione distinta**. Un'interruzione fra le due lascia schema aggiornato senza registrazione; il retry può ripetere la migrazione o fallire su oggetti già esistenti. Anche il controllo preliminare del checksum è separato, quindi due esecuzioni concorrenti non sono serializzate.

Intervento: controllo versione sotto lock, SQL e registrazione nella stessa sessione/transazione. Accettazione: test di rollback, retry e concorrenza su database isolato; nessuna migrazione applicata senza il suo record. È un difetto del runner verificato nel codice, non la prova che il database attuale sia incoerente.

### 3. Alta — completare l'export account oltre il limite API

`app/api/auth/export-account/route.ts:18–31` legge intere collezioni senza paginazione e costruisce l'elenco delle partite solo dalle partecipazioni ricevute. `supabase/config.toml:8` imposta `max_rows = 1000` nell'ambiente del repository. Superando il limite del server, l'export può restituire HTTP 200 con dati mancanti. La query `.in('id', matchIds)` concentra inoltre tutti gli ID in una richiesta.

Intervento: paginare con ordine stabile e raggruppare gli ID in blocchi; verificare conteggi e coerenza durante l'esportazione. Accettazione: fixture con oltre 1.000 partecipazioni/notifiche restituisce tutti i record, senza duplicati. Il limite effettivo della VM e la presenza di utenti già interessati non sono stati verificati.

### 4. Media — riallineare aggiornamenti consigliati e note pubbliche

La GET pubblica `/api/app-config` restituisce `currentVersion=9.0.4`, `recommendedVersion=8.2.0` e note della 8.2. `lib/version-policy.ts:23–26` determina la disponibilità dell'aggiornamento dalla versione consigliata: un client 8.2 o superiore può quindi non ricevere il suggerimento per la 9.0.4.

Intervento: aggiornare la configurazione runtime nell'ambito di un rilascio autorizzato, mantenendo separato il minimo supportato (8.1.0). Accettazione: client 8.2 riceve `update_available`, 9.0.4 resta supportato; note coerenti con la release. Rilievo già presente nell'audit del 22 settembre e ancora aperto.

### 5. Media — verificare gli allegati realmente pubblicati

La [release v9.0.4](https://github.com/marco201091-glitch/21life/releases/tag/v9.0.4), interrogata con `gh release view`, contiene **solo `21life-v9.0.4.apk`**. Il workflow prevede anche checksum e due SBOM; la checklist dichiara IPA unsigned e checksum pubblicati, ma non sono presenti in questa release. GitHub espone comunque il digest SHA-256 dell'APK.

Il workflow usa `gh release create`, senza gestire una release già esistente. La PR aperta [#117](https://github.com/marco201091-glitch/21life/pull/117) affronta questo caso. Non è stata dimostrata qui la causa specifica degli allegati mancanti.

Intervento: pubblicazione ripetibile, controllo finale degli asset obbligatori, aggiornamento della checklist sulla base della release effettiva. Accettazione: checksum/SBOM scaricabili e coerenti con l'APK; chiarire dove distribuire l'IPA prima di dichiararla disponibile.

### 6. Media — aggregare le metriche operative nel database

`app/api/admin/operations/route.ts:28–30` scarica fino a 10.000 righe per accessi, notifiche e telemetria, poi aggrega in JavaScript. `queryLimited` si attiva solo raggiungendo esattamente 10.000 righe: un limite PostgREST inferiore può troncare la risposta senza far comparire l'indicazione. Le query non hanno un ordine che definisca il campione troncato.

Intervento: aggregazioni SQL autorizzate oppure paginazione completa, con conteggi e stato di completezza espliciti. Accettazione: statistiche esatte su fixture oltre il limite API e oltre 10.000 righe. Non sono state misurate discrepanze reali sulla VM.

## Ordine proposto

1. Chiudere advisory Next.js, atomicità migrazioni e completezza export.
2. Rendere coerenti configurazione aggiornamenti, allegati release e metriche operative.
3. Ampliare test mobile e prove di ripristino; poi refactoring incrementale delle schermate e consolidamento F-Droid.

## Limiti e comandi

Revisione mirata di autenticazione server `getUser`, autorizzazione admin, cancellazione account con revoca sessioni, policy della richiesta Archidekt, runner migrazioni, backup e workflow. Nessun bypass di autorizzazione confermato nei percorsi letti; questo non costituisce una verifica completa delle RLS effettive.

Non eseguiti: pen test, accesso SSH, query sui dati utenti, verifica dei privilegi effettivi in produzione, restore, benchmark, nuova build completa, nuovo E2E locale, prova manuale su dispositivo, verifica firma del binario scaricato o revisione UX con utenti. Per build/E2E si riutilizza la CI sul medesimo codice. Nessuna stima di prestazioni o usabilità viene presentata come misurata.

Comandi principali: `git fetch/diff/rev-list`, `gh run list/view`, `gh release view/list`, `gh pr list/view`, API protezioni branch, due `npm run quality`, due audit npm produzione, `node scripts/verify-obtainium-readiness.mjs --release`, ricerche statiche e GET pubbliche readiness/app-config.
